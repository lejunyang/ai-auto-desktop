# 飞书（Lark/Feishu）桌面客户端观察实测

日期：2026-09-27，版本 8.1.17（官方 release，安装在 `E:\Feishu\app\Feishu.exe`），已登录、主窗口可见。用 `aad apps/snapshot/watch` 直接对真机取证。

## 1. 它是什么

飞书 PC 是**字节自研的 Chromium 分支（代号 iron，见 manifest `native-iron-*`）+ 大量 asar 前端包**，不是标准 Electron：
- 安装目录有 `frame.dll/liblark.dll`、`webcontent/*.asar`（messenger 69MB、calendar、space、bitable 等）、窗口类名是 `Chrome_WidgetWin_1`，可访问性树 `framework_id=Chrome`（152 节点里 41 个）。
- 多进程，主进程 25752，另有一个 127.0.0.1 内部端口（非 CDP，握手即关闭）。

## 2. 三路结果

| 路线 | 结果 |
| --- | --- |
| 默认 UIA 树 | **外壳与会话列表完全可读**；**打开的聊天正文与输入框不暴露内容** |
| CDP `--remote-debugging-port` | **不可用**：单例在运行时该参数被忽略（启动器直接退出交回现有实例）；完全退出后带参冷启动也**不开端口**；`ELECTRON_EXTRA_LAUNCH_ARGS` 环境变量同样无效。飞书在 iron 层禁用/移除了远程调试入口 |
| 屏幕阅读器模式 | UIA 客户端接入后辅助功能已是开启状态（树非空），但聊天正文 document 节点 value 仍是 `file:///…/messenger-chat/zh-CN.html`，**没有 VS Code 那种"开无障碍即出全文"的开关证据** |

### 2.1 UIA 能读到什么（实测节点）
- 顶部/侧边导航全部：`搜索（Ctrl＋K）`、`创建`、`消息/豆包工作/日历/云文档/多维表格/视频会议/工作台/通讯录…` tab_item、最小化/最大化/关闭。
- **会话列表的真实文本**（text 节点 47 个）：每个会话的名字、时间、最后一条消息预览，例如：
  - `豆包工作 00:13 嗨，我是豆包，可以帮你解答问题…`
  - `账号安全中心 9月18日 安全登录通知`
  - `飞书助手 …迎新春！V7.36 多维表格 Logo 焕新…`
  - `云文档助手: @勒俊阳关注飞书的上手指南…`
  - 系统消息 `消息超出可保留期限，已被删除`、`欢迎 勒俊阳 加入…` 等。
- webview 容器：`MultiWebView - messenger:messenger-chat:default` 等，能区分当前在哪个模块。

### 2.2 UIA 读不到什么
- 打开的会话里**逐条消息正文**和底部**输入框内容**：只有两个 document 节点，value 是本地 html 文件路径，正文不在树里（与 VS Code 默认同型，但飞书没找到可切换的全文开关）。
- 12 秒 `aad watch --window <飞书>` 期间点击会话列表，digest 没有产出（该视图列表本身已完整加载、点击只是切右侧 webview，右侧内容又不进树）。

## 3. 结论与路线选择

- 飞书**走不了 CDP**（铁证：冷启动也不开调试端口）。
- 现状靠 UIA 可监控：**你在哪个模块、切到哪个会话、会话列表的标题/时间/消息预览、顶部搜索与导航点击**；但**具体聊天里收发的正文、你在输入框打的字**默认拿不到。
- 要拿到聊天正文/输入，候选只剩：
  1. **截图 + OCR / UIA 区域文本兜底**（项目已有 aad-ocr 与截图设计）：对聊天消息区、输入框区域取图识别。这是对这种自绘/封闭 webview 最现实、且不违反其安全策略的路径；成本是准确率与隐私。
  2. **飞书开放平台 API/机器人**：能合规读取消息，但需要企业应用授权、且拿不到"你此刻在界面上的输入/点击"这种行为流，定位不同，不适合本地观察。
  3. 逆向 iron/asar 注入：明确不做（违反安全/条款，也脆弱）。

建议：飞书正文走"UIA（导航+会话+预览）+ 定向 OCR（聊天正文/输入框）"，并在文档里把飞书列为"无 CDP、正文需 OCR"的代表；浏览器与（开启无障碍/调试的）Electron 仍走 CDP/UIA。
